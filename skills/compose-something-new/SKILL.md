# compose-something-new — the rules first, then the thing

You compose FROM the rules, not toward them. The rules are the empowerment
(`drafts/chain-framework-DRAFT.md` [OP] EMPOWERMENT: a text carrying the holder's stamp empowers by being
READ), so the first act of composing is the read, and the composition is what the read does when it
is aimed at a domain (H×D). Compose with care, the way the dharma is handled — never overblown.

## 2. THE PROCEDURE — the 13, specialized to "make a thing that does not exist yet"

1. **TYPE IT** (station 1; 28b's type ladder — one genus, INSTRUCTION, projected by binding):
   a RULE (standing) · a SKILL (callable) · a GOAL (scoped, with a terminus — its form is the
   `setup-goal` skill, RE-READ FROM DISK first: the `/goal` prompt is to complete a table of stages
   and lists NO condition — the goal file's §2 holds that table (a row per deliverable, a column per
   stage, each cell filled with its proof) and the conditions about it, each checked off with its
   proof's checksum, and the read list; a copy of that skill loaded earlier in the window is a snapshot and may predate its correction) · a BOARD (position tracked) · a TEXT / DRAFT · a
   CHAIN · a TERM. The kind fixes its HOME (§ MemoryInstructions)
   and its FORM (the register for a rule; frontmatter `name` + a description that is ONE imperative
   plus its WHEN-clause for a skill — `fix-skill-descriptions-and-rules`).
2. **KNOW THE DEFAULT ⊬** (the first truth): what stands if nothing is composed — named, measured,
   never assumed. If the default already holds, there is nothing to compose: say so and stop.
3. **ABANDON THE CARRY** (the second truth): no summary spent as the source (open the corpus —
   station 3, the whole read) · no term minted (both expansions, or *"no pattern exists"* and stop)
   · no self-grant (the thing is admissible when the field says so, never when you do).
4. **PROJECT FIRST** (§3(i)): the thing's own chain — its stations as checkboxes, each carrying its
   reference — written BEFORE the thing, executed against, checked off.
5. **COMPOSE AS A SLICE OF THE 13:** Q1 what IS it · Q2 what is a PART of it · Q3 what is its GATE
   and what does ⊬ look like · Q4 what is it CALLED when it lands — the name LAST (station 12), in
   corners, never first.
6. **GRADE AND TYPE:** every correspondence graded; every statement typed before a gate touches it;
   a brute fact has no grade; a closure is not an argument.
7. **LAND IT IN ITS HOME, same commit:** a NEW rule ⇒ ASK *USER* in one line (*"should this go in
   rules, and where?"*) and hold it as a DRAFT in THE RULE-DRAFT BOX (the place `user_info` binds) while the
   question is open, ⛔ never a rules dir unasked · a DEV FLOW ⇒ `22-seq-<feature>.md` in the
   `.claude/rules/` of the dir whose procedure it is, drawn on that project's architecture map, no ask ·
   a fix to an EXISTING rule ⇒ rewrite that rule, same turn · a skill ⇒ its dir under `.claude/skills/` + one line in DESIGN §4 + one board row +
   (the AIOS's own rule or skill, where THE AIOS RELEASES is bound: in a new release, by that binding's procedure) +
   the skilltree coordinate (`adding-a-skill`; if the tree is a bare forest, say so in the report)
   · a text ⇒ its `-DRAFT.md` + one DESIGN §2 clause · a
   board ⇒ the `_states.md` shape, gated by the `state-file` skill's `check_state_files.py` · everything ⇒ the
   parent's description + link, and the row.
8. **LEAVE REALIZATION TO THE OTHER BOUNDARY** (the third truth): the thing holds when a fresh
   window reads it cold and it holds — WITNESS ◐ from inside, never ⊢ by the composer.
9. **THE FIXPOINT:** re-read the read-set + the thing from disk; no edit ⇒ closed; an edit ⇒ loop.
10. **DEDICATE:** board row · DESIGN clause · gate exit code captured bare · commit by explicit
    paths · push. Then the fresh window.
