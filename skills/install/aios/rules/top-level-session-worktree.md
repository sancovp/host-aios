# Work is saved in the copy in use; code is changed in its own worktree; nothing is lost on any pull

SCOPE:[binds the developer agent's own world — THE WORLD DIR, its repositories and its sessions — never a product's agents (a JobWorld seat or box, OM) or a customer's repositories, which follow their own product's design]

CONTEXT:[operational half of [[repo-canonicity-and-publishing]] (WHERE work lives = THE CANONICAL HOME, one hot home); this = HOW the hands that touch one checkout share it · extends [[subagent-worktree-isolation]] up to top-level sessions]
PRINCIPLE:[**A MULTI-PROJECT REPOSITORY SHARES ONE `.git`/default branch/index/HEAD ACROSS ALL ITS SUBDIRS** · git ops (`add -A`, `commit`, `pull`, `push`, HEAD) are repo-global, not subdir-scoped · separate subfolders do NOT isolate — sessions in one checkout collide on git STATE · ⇒ sessions that share a checkout each commit only their own paths and never move its branch, and every change to code is made in a worktree of its own · this binds hardest where the canonical home holds many projects, which is the shape [[canonical-source-dirs]] LAW 0 describes]

LAW:[
- THE TWO KINDS OF CHANGE — every change is one of them, and where it is made follows from which:
  - **WORK** — documents, notes, records, boards, and a project's outputs — what using it produces, and everything made
    for one piece of it, whatever it is made of: an essay, a render, a report, the record of a meeting or a run, a
    film's script, its scenes and the code that makes its assets — in its own `workspace/` folder, sorted there by kind and made as the
    work goes (the skill `how-to-save-work`); a note about undone work goes to the project's scratchpad. It is made in THE COPY IN USE: the checkout on
    the default branch that runs, and that the AI using the thing stands in. It is saved by its own paths —
    `git add -- <its paths>` (a new file is untracked until then), then `git commit -m "<message>" -- <its paths>`,
    never `git add -A` — and pushed to the default branch the same turn, no worktree, no pull request. A work path sits
    outside every folder the installation publishes and outside every application that deploys when its default branch
    changes — or inside a project's own `workspace/`: at once where nothing that acts when the default branch moves
    reaches that project; where a publisher or a deploy reaches it, once that system leaves the project's own
    `workspace/` out — of its copy, its change check and its choice of what a change touches — as its own design
    states with no `ASPIRATIONAL:` mark, and until then the project's work is saved beside its folder, never inside
    it. Nothing in a workspace is published but a folder named on purpose as a published artifact in the publisher's
    list. The project's program is never changed in a workspace. A project's scratchpad and notes are work; a goal file its writer puts
    on the default branch is work.
  - **CODE** — a change to what the next piece of work is made with: the project's own program — its code, its skills
    and rules, its libraries and packages, what packs its work into reusable, distributable things; when that test
    cannot tell, the change is code. It is made only in THE DEV SPACE, which is worktrees: a worktree of the project's
    repository off the upstream default branch, inside THE WORLD DIR, in a folder its repository ignores, never under
    the system's temporary folders ([[subagent-worktree-isolation]]), on its own branch — developed there, merged, and
    pulled back into the copy in use. A session in a worktree keeps this AIOS's context, the worktree's own
    instructions loading beneath it. Only a change at the AIOS's own level — to the AIOS every session here loads, where
    two copies of it would otherwise load — is made from a seat that loads none of it: its settings keep out every
    instruction file above it (a settings file's `claudeMdExcludes`), and the user's settings and tool servers
    (`--setting-sources project,local`, `--strict-mcp-config`); a project never needs that seat. A folder added to a
    session with `--add-dir` brings in its `CLAUDE.md` and rules only when `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`
    is set, so no seat counts on `--add-dir` alone to load them. A version under development runs in an environment of
    its own, never in the copy in use. Code reaches the default branch only as a version (point 13),
    through the merge queue. A goal run's own records — its goal file's table, its proofs, the boards its work moves —
    belong to the version it ships and travel with its code, so the default branch keeps the writer's goal file to be
    checked against.
- several sessions save into one copy in use: none of them switches its branch, resets it, or commits a path it did
  not change — a file another session changed and has not committed is that session's, whatever is found on sight ·
  a commit refused because the index is locked waits and tries again
- THE GIT LOOP IS THE AGENT'S, END TO END — *USER* does not do git; the CI's design is the canonical home's `automation/cicd-reviewer/DESIGN.md`:
  1. FIRST, before any work on a repo: read that repo's rows in the `UNMERGED WORK` issue on the canonical home and `gh pr list --state open`; clear your own PRs and the repo's STUCK rows before new work · then pull the copy in use again by point 12, so no work is made on code that is not current · while THE CI's runner starts no job no sweep writes those rows: every ready pull request `gh pr list` shows there is the queue, and you land it by point 3 before new work
  2. WORK is committed by its own paths and pushed as it is made; a push refused because the default branch moved is met by pulling by point 12 and pushing again · CODE: work in your worktree and commit as you go; push its branch only when the set of code is done, or once before the session ends so nothing is lost — never per edit · ⛔ NEVER PUSH CODE TO THE DEFAULT BRANCH of a repository with a merge queue — every such push skips the review · ONE set of code = ONE branch = ONE ready PR, opened when the whole set is done (open one as a draft only if the work should be visible while it is in progress)
  3. **A VERSION IS DONE ONLY WHEN IT IS ON THE DEFAULT BRANCH, AND ONLY THE MERGE QUEUE MERGES IT.** A pushed branch, an open PR, a green test is not done · while THE CI runs, a session never merges — a session merging its own PR races the review · **while THE CI's runner starts no job, the session IS the CI and lands every merge:** it runs the CI design's QUEUE BY HAND over every ready pull request the stop holds up, its own included — every review already on the exact tip read first, the diff read whole, its verdict posted on that tip as a review comment, a clean, fresh one squash-merged at that tip (`gh pr merge <n> --squash --match-head-commit <sha>`, alone in its call — never with `--delete-branch`, which the harness refuses), its branch then deleted in a call of its own (`gh api -X DELETE repos/<owner>/<repo>/git/refs/heads/<branch>`), and labelled for the late review · a pull request the harness will not let the session that opened it merge is merged by the next session that holds the CI · nothing about the stop, the queue, a held pull request or a merge is ever put to *USER* — not asked, not handed over, not parked
  4. **HAND OFF WHEN THE CODE IS DONE** — made a version by point 13, its checks run: merge the default branch into your branch (resolve every conflict, keeping both sides' work; never drop the other side's lines), push, and open the PR READY — or mark your draft ready. That is what asks for the review: the reviewer gives it a verdict on its exact tip, and the merge queue merges a `VERDICT: CLEAN` that is still fresh, one at a time, overlapping PRs ordered by its coordinator
  5. **WAIT FOR IT WHILE YOU RUN — THROUGH THE PR WATCH, NEVER A LOOP OF YOUR OWN** (while THE CI's runner starts no job nothing moves it: land it by point 3, then confirm it as below): run THE CI's PR watch ([[user_info]] binds THE CI) in the background, naming the PR and your last pushed commit; it exits once, with one line naming what to do, on MERGED · CLOSED · CONFLICT · BLOCKING · a failed review run · a review run stalled in the queue · a new comment · a moved tip · its cap — act on that line, and start it again only if the PR is still open and something is moving · a `VERDICT: BLOCKING` you fix and push (one new review) · a review run that failed you re-run when GitHub failed to start it, and land by point 3 when Actions refused its jobs · a review run stalled in the queue (REVIEW-STALLED) you start again by marking the PR draft, then ready · a conflict comment you resolve by merging the default branch in, then push · a hold names what to change · then confirm the PR is MERGED AT YOUR LAST PUSHED COMMIT — `gh pr view <n> --json state,headRefOid` equals `git rev-parse <branch>`; a commit pushed after the queue took the PR is on no default branch, so carry it in a new PR — then pull the copy in use again and install what the version changed, by point 12, and remove your worktree and local branch only as point 12 allows (the queue deletes the remote branch; by hand, point 3's call of its own deletes it)
  6. a session that must end before its PR is MERGED says so in its report, as the CI's work and never as a question or a step for *USER* — the daily sweep lists it in `UNMERGED WORK` and the next session in that repo clears it first; while THE CI's runner starts no job, the next session that holds the CI lands it by point 3
  7. only where a repo's own rules put work straight onto its default branch and it has no merge queue, commit there and push, code included; every other repo's code goes through the queue
  8. **NEVER FORCE PUSH** — not to the default branch, not to any shared branch; a conflict is resolved by merging, never by overwriting
  9. a dispatched agent hands nothing off: it changes no code that lands, its change to code staying in a throwaway copy the dispatching session reads and removes ([[subagent-worktree-isolation]]); the work an agent a lead starts writes for its child project is saved by that lead, by its own paths, with the child's cell (the `how-to-lead-an-aios` skill)
  10. before your final report: in the copy in use `git status --short` shows nothing of yours unsaved and `git log origin/<default>..<default>` is empty; `git branch` and `git worktree list` show nothing of yours except PRs handed off and waiting on the queue — name each one
  11. a rule or skill of the AIOS merged this way reaches the running machine only through a new release, where [[user_info]] binds THE AIOS RELEASES, made and promoted by that binding's procedure; where it is not bound, only when the checkout its symlinks point at pulls — pull it by point 12 when it is clean; when another session holds it dirty, say so and leave it
  12. **NOTHING IS LOST ON ANY PULL.** A pull happens at the start of work in a copy in use, after every merge, and before the copy is used as a diff reference. Before it: every change of YOURS in the copy in use is committed by its own paths and pushed, so nothing of yours exists only on this machine, and the head is recorded (`git rev-parse HEAD`); another session's uncommitted changes are left where they are — the pull adds around them, or git stops it naming the file, and then you report it and wait, never force. The pull only adds: `git pull --ff-only`, and when both sides have moved, `git pull --no-rebase` — a merge that keeps both sides, every conflict resolved by keeping both; a merge commit on the default branch moves no session off it. Never `git reset --hard`, `git checkout -- <path>`, `git restore`, `git clean`, `git stash -u` ([[never-stash-u-to-test-a-baseline]]), a rebase of pushed commits, or a force push. After it: `git merge-base --is-ancestor <recorded head> HEAD` → true; anything else is reported at once and nothing further is done. Every merge is pulled into the copy in use this way, and what it changed is installed into what runs it — a program left running is restarted on it by its pid and checked to answer ([[kill-by-pid-never-by-pattern]]), THE PRECIOUS STORE never ([[the-precious-store]]). A worktree is removed — `git worktree remove`, never `--force` — only when `git -C <worktree> status --short --ignored` shows nothing that cannot be rebuilt (a venv, `node_modules`, `__pycache__` can; anything else is moved to its place first) and its PR is MERGED at its last pushed commit, or its branch is pushed with `git -C <worktree> rev-list origin/<branch>..HEAD` empty; git removes a worktree that holds only ignored files without `--force`; one it refuses holds an untracked or changed file — find it and move it to its place, then remove. Its local branch is deleted with `git branch -D` only after that. A worktree holding commits no default branch has is named in the report and left, with the one step that lands it: its work onto the default branch by point 2, its code as a ready PR by point 4.
  13. **MAKING A VERSION.** In the dev space: the change made and tested in its environment → the version raised in the program's build file (`pyproject.toml`, `.claude-plugin/plugin.json`) and its `CHANGELOG.md` entry written → every check for the kinds of file it changes run and passed — the checks [[00-docsys]] names in THE PATTERNS UP FRONT, so the version reaches its repository's reviewer already following its patterns → sent to the repository's default branch: a ready PR where the repository has a reviewer and merge queue (point 4), a push where its own rules put code straight on its default branch (point 7) → watched through the review (point 5), every finding fixed → merged by the merge queue, confirmed MERGED at your last pushed commit → pulled into the copy in use and installed into what runs it (point 12) → where the installation's publisher is set up, it publishes what changed by itself. A work file carries no check and is never a version.
- THE STANDING BRANCHES: in the canonical home, a branch other than the default stands only when [[user_info]] binds it as another machine's lane; no session on this machine pushes to another machine's lane or merges into it — work built on it is a FORK, a branch off it under its own name, kept separate until its work reaches the default branch by porting the files it needs onto a branch off the default, handed off like any other; every other branch in any repo is unmerged work, to be merged to the default branch — never left, never treated as a home
- a worktree = same repo/origin/history, own working dir + branch + index + HEAD (single-source-of-truth AND per-change git isolation)
]

MECHANISM (the SessionStart/SessionEnd hooks):[
these two hooks do NOT ship with this AIOS — their shape is stated so an installation can build them;
until one exists, the LAW above binds by hand.
- **a SessionStart hook, matcher `startup`**: in a copy in use, pulls it again by point 12 and reports what came in and every worktree still open · FAIL-SOFT (any failure exits 0 + a note, never exit 2)
- **a SessionEnd hook**: reports any WORK left uncommitted or unpushed in the copy in use and any worktree of the session not yet merged; removes nothing
- LIMITATION: a hook cannot change cwd — it PREPARES + INJECTS; it never resolves what it finds
- INSTALL (user's call — a global SessionStart hook affects every session): register both in `~/.claude/settings.json` under `hooks.SessionStart` (matcher `startup`) + `hooks.SessionEnd`
]

TRIGGER:[saving any work (⇒ by its own paths, pushed the same turn; an output of using a project ⇒ `how-to-save-work`) · about to change code (⇒ a worktree of its own; the seat that loads none of the AIOS only for a change at the AIOS's own level) · about to send a version (⇒ point 13, its checks first) · two+ sessions working in one checkout · starting ANY work on a repo (⇒ its open PRs first) · code done (⇒ hand it off as a READY PR; while THE CI runs, wait for the merge queue and never merge it yourself; while its runner starts no job, land it yourself by point 3) · any pull (⇒ point 12) · about to remove a worktree (⇒ point 12) · when in doubt whether a change is work or code → ask whether it alters what the next piece of work is made with; yes, or no telling ⇒ code: make a worktree]
