# One canonical DESIGN.md per project — DESIGN.md ONLY, the head of a design system that covers every file of the code, every other document wired under it, each opening with its READ ORDER

<docsys kind="design" role="law"/>

TRIGGER:[creating or naming any design/spec doc (⇒ it is DESIGN.md or it is a detail doc with a pointer) · a file added to, renamed in or removed from a project's code (⇒ its line in the design — why it exists, what it connects to — the same change) · a question about a project that its `DESIGN.md` and the pages it links cannot answer (⇒ a page is missing: write it, then answer from it) · an explanation outgrowing its section (⇒ a page of its own in `design/`, linked from the section) · creating ANY document — a detail design, a pattern, a reference, a note's record (⇒ its line in its parent design, the same commit) · any architectural change (⇒ DESIGN.md in the SAME commit) · a child `DESIGN.md` added, renamed or removed (⇒ the parent's READ ORDER rewritten, the same commit) · finding a doc that contradicts DESIGN.md · a feature not yet built (⇒ its row on the project's board, short of its last state; the design states it as part of the final state, in the step or version that brings it) · a design found holding a current state (⇒ each passage of it fenced where it stands, every word unchanged; moved into its boards as rows when its project is next worked on) · about to delete a design doc (⇒ roll IN, leave a pointer; deletion is *USER*'s per-file call) · about to write a ruling into a note, or into a document nothing loads where the ruling fires]
CANONICAL DOCS (the only three in the entire tree):[
1. each top AIOS's TOP-LEVEL DESIGN — the cover over every `DESIGN.md` beneath that top, outside its home-unknown band; THE MASTER MAP names every top ([[00-canonical-doc-paths]])
2. the `DESIGN.md` of each PROJECT — **a project is ONE ENTITY: its own abstraction, running on its own context; a different abstraction is a different project, with or without code of its own** (a codebase is one kind of entity; the network that sells products, the deployment that runs them for customers, a book, are projects exactly as a codebase is; a concern spanning several codebases is its own project, never a section of each codebase's design) — **ONE per project, never one per dir** (agent-rts has ONE; `render/`, `feeders/`, `examples/` do NOT get their own — a subdir's design is a SECTION of its project's DESIGN.md). A project NESTED inside another (exoblend inside agent-rts) is its own project and keeps its own; a sub-PACKAGE (the wow pack inside cave-teams) is not — it rolls up.
3. each top's TOP-LEVEL STATES DOC — that top's OUTSTANDING ledger ([[28-distributed-state]])
]
THE DESIGN COVERS EVERY FILE OF THE CODE:[the design is a system of documents with one head, and it is what is read instead of the code · every file that exists in the project's code — its modules, its scripts, its tests, its build and container files, its hooks, the scripts its skills carry — has its line in the design: why the file exists, and how it connects to everything else, each connection named · an explanation too long for its section is a page of its own in a `design/` folder beside `DESIGN.md`, linked from the section that owns its topic and listed in that folder's `CLAUDE.md` · any question about the project is answered from `DESIGN.md` and the pages it links; a question they cannot answer means a page is missing, and writing it is the work, never reading the code again · a file added to, renamed in or removed from the code is added to, renamed in or removed from the design in the same change · a program checks it: the `design-md` skill's `check_design_covers_code.py <project>` lists every code file that neither `DESIGN.md` nor a page it reaches names]
EVERY DOCUMENT IS A DESIGN DOCUMENT, WIRED UPWARD:[the project's one `DESIGN.md` is the root of its designs · every other document — a detail design, a pattern, a reference, a note's record — sits under a parent design that carries its one-line summary and its link, summarized again at each level up to the top-level design ([[every-level-describes-and-breadcrumbs-below]]) · a document nothing reaches does not bind, so a ruling goes into the document that loads at its trigger, never into a note · a program checks it: the `top-level-design` skill's `check_reachable.py`, run from a top-level design or a `DESIGN.md`, lists every tracked `.md` file nothing reaches]
EVERY DESIGN.md OPENS WITH ITS READ ORDER:[under the heading `READ ORDER`, first: what this level is, and for which work which child design and which procedure (dev flow, skill) to read · its last line `ARCHIVE AND PROGRAM FOLDERS:` naming the folders whose files are evidence, generated output or a program's source — run evidence, records, goals and their proofs, forks, a generated package, a template — which the read-order check and the reachability check skip, `none` when there are none, and which exempts no code · where the project holds code that is a copy of code living elsewhere, the output of a generator or the evidence of a run, one more line, `COPIES, GENERATED OUTPUT AND RUN EVIDENCE:`, naming those folders, the only code the coverage gate leaves unchecked besides build output, the project's own `workspace/` and a child project's folder · it names every child `DESIGN.md` beneath it outside the archive and program folders · it is rewritten in the same commit as any child design added, renamed or removed · a program checks it: the `design-toc` skill's `design_toc.py <project> --check`]
DO:[
- OPEN THE `design-md` SKILL FIRST — the Skill tool, by its name, before the first write of a DESIGN.md — and author or repair the DESIGN.md through it — the skill is the HOW, this rule the WHAT; open the `design-toc` skill the same way at every edit of a `DESIGN.md`
- name every canonical DESIGN document `DESIGN.md` (nothing else)
- roll a `XYZ.md` design/spec doc's content INTO the DESIGN.md of the project it sits in, then leave the source as a pointer
- give every new document its one-line summary and link in its parent design — the section that owns its topic, or the folder's `CLAUDE.md` — in the same commit that makes it
- treat DESIGN.md as the single source of structural truth: the intended final state of what it designs and the steps or versions by which it evolves, in order (a decision not in it does not exist)
- give every file of the project's code its line in the design — why it exists, and what it connects to, each connection named — in the section that owns its topic, or in a files page of `design/` that section links; write each file by a name no other file shares
- move an explanation that outgrows its section into a page of `design/`, leave the section its statement and a one-line link, and list the page in that folder's `CLAUDE.md`
- answer a question about a project from its `DESIGN.md` and the pages it links; where they cannot answer it, read the code that does once, write the page, link it, then answer from the page
- keep DESIGN.md the thing the code is checked against: it holds the intended final state, and only that, so any reader can hold it beside the code and ask one question — is this implemented as it says, or as it implies? — so it is never rewritten down to describe broken, partial or stubbed code and never records current state; where the code falls short, the shortfall is a row of the project's board and the design stands
- update DESIGN.md in the SAME commit as any architectural change, its READ ORDER with it, and append what changed, the reading it replaced and why to the `CHANGELOG.md` beside it — DESIGN.md itself states only the design: the final state and its steps
- state a part not yet reached as part of the final state and, where it comes later, in the step or version that brings it; whether a part is reached is a row of the project's board, never a mark or a sentence in the design
- fence every current state a design is found holding — built or not, how far, measured, missing, in pieces — where it stands: the whole passage that holds it (the paragraph, list item, table or section, never part of a sentence), every word unchanged, between the line `> **WARNING: STATE MENTIONED IN DESIGN.MD -- NOT ALLOWED IN DESIGN. THIS MUST MOVE TO STATE FILE WHEN WORKED ON. DO NOT REMOVE THIS FENCE UNTIL THE STATE IS RECONCILED AND EVERY INTENDED THING IS BUILT AS INTENDED. DO NOT SKIP THIS.**` before it and the line `> **END OF STATE FENCE**` after it, each written as one line · find that state by reading the design, never by a program · when the project is next worked on, move each fenced passage into its boards as rows, defining any state it needs, and remove the fence only once the state is reconciled and every intended thing is built as intended
- make other docs excerpt/link/point to DESIGN.md
- banner a reference-detail doc "REFERENCE DETAIL — READ when its topic is the active task; NOT deprecated, NOT skippable" · keep it fully in the doc tree (read, drilled as a breadcrumb, the DETAIL layer under DESIGN.md's rows)
- before a version leaves, run the coverage gate and the read-order check on the project and the reachability check from the design, bare, and act on what they say ([[00-docsys]] THE PATTERNS UP FRONT)
]
NOT:[
- write a current state into a design — built or not, how far, measured, missing, in pieces — or mark a part as not reached, by a word, a tag or a sentence
- reword or split a fenced passage, or remove its fence before its state is reconciled and every intended thing is built as intended
- name a canonical DESIGN doc anything but DESIGN.md
- leave a file of the code with no line in the design, or add, rename or remove a file without the design moving in the same change
- answer a question the design should hold by reading the code again and writing nothing down
- name the code a design is the design of on the `COPIES, GENERATED OUTPUT AND RUN EVIDENCE:` line
- take the coverage gate's pass as proof that a file is explained (it tells that a file is named; whether its line says why it exists and what it connects to is judged by reading)
- let another doc contradict DESIGN.md
- leave a document no parent design or folder index links, or write a ruling where nothing loads it at its trigger
- leave a `DESIGN.md` without its READ ORDER, or a child `DESIGN.md` its READ ORDER does not name
- delete anything under this law (roll IN, leave a pointer; deletion is *USER*'s explicit per-file call)
- treat `.claude/rules/*` or a `CLAUDE.md` as a design doc under this law (they are LOADING MECHANISMS, never renamed or rolled into a DESIGN.md — a folder's `CLAUDE.md` still carries its one line for each file and folder in it)
- banner a doc bare "NON-CANONICAL" (reads as "skip this", teaches skipping load-bearing detail)
]
